# AHJ Atlas

A local HTML/CSS/JavaScript application for source-linked AHJ, professional contact, code-adoption, and submission research. The Windows desktop build includes its own Electron/Node runtime; source development uses Node.js 24. No hosting subscription is required.

## Windows installer

Download the unsigned, per-user Windows x64 installer and its checksum from a [published GitHub Release](https://github.com/Abe-Borg/ahj-atlas/releases). Follow the [Windows installation guide](docs/windows-installation.md) for checksum verification, the unsigned publisher warning, installation, upgrades, backup, and removal. The installed app includes its runtime; installed users do not need Node.js, `npm`, or the `.cmd` launchers.

Research and chat require internet access and an Anthropic API key. Ordinary search and source reading do not require Edge or Chrome. The optional JavaScript page renderer currently uses an installed Edge or Chrome browser.

## Source development

Source development requires Node.js 24 or newer. Run `npm ci` in this checkout, then use `npm start` to keep the local backend in a terminal. On Windows, **Start AHJ Atlas.cmd** starts a hidden backend at http://127.0.0.1:4318 and opens the system browser; **Stop AHJ Atlas.cmd** drains in-flight work and stops it. Closing only the browser leaves that source backend running. These launchers are for source users, not installed-app users.

In **API & spending**, enter an Anthropic API key with access to `claude-sonnet-5-5` and `claude-opus-5-5` for new work. Enable web search in the Anthropic Console. The connection checks the key through Anthropic's Models API; each request checks access and capabilities for its actual model before a paid response is generated. An in-progress Sonnet 5 conversation can continue with a key that still has access to its original model. A Chat subscription does not replace API access.

The sidebar connection button shows **Claude connected** only after Anthropic accepts the key. It shows **Claude disconnected** when no key is entered or when Anthropic refuses the key (for example, an unauthorized key or one without permission to list models). A remembered key is checked again each time the app starts. While the app runs, any request Anthropic rejects as unauthorized (for example, a revoked key) also switches the button to **Claude disconnected**. A request that was already running before the rejection cannot switch it back to connected when it finishes; only a request started later can. **Checking Claude…** appears briefly while a remembered key is being checked. **Claude unavailable** means the key could not be checked because Anthropic could not be reached or returned a temporary error (such as overloaded or rate limited); the app checks again while it is open, starting after one minute and backing off to every 15 minutes. Hover over the button, or open **API & spending**, to see the reason. New projects created while the key is missing or rejected wait for a working key. `node --test tests/provider.test.mjs` covers these states, and `node tests/connection-ui.mjs` checks the button in a browser without a real key.

Enter the required project name, address and discipline, optional scope, building use, permit date and parcel number (APN) or site description, and processing mode. Choose **Other — enter your discipline** for a specialty not listed. **Building use** (under **Add project context**) is a dropdown that defaults to **Hyperscale data center**. Choose another listed use, **Not yet specified** to leave it blank, or **Other — enter building use** to type your own (2–100 characters). The report includes authorities, professional contacts, adopted editions, local amendments, permit requirements, source passages, and unresolved questions. PDF, native XLSX, and JSON exports are supported even for partial research.

To remove a project, open it and choose **Delete project**, then confirm. This permanently removes its saved report, sources, answers, and chat history; export anything you want to keep first. Stop active research or chat and let outstanding requests finish before deleting. Uncertain charges must be resolved in **Activity**. Recorded charges stay in the workspace's estimated spending totals.

## Correcting the project address

A project's address can be corrected without deleting the project: for example a typo, a wrong ZIP code, or a new-tract site that receives an assigned street address after research has started. Open the project and choose **Continue research** (or **Review or extend report**). The dialog shows the saved **Project address** and an optional **Parcel number (APN) or site description**. Edit either one and continue. The address is validated the same way as on a new project: 8–500 characters after trimming. The site description (up to 500 characters) can hold an assessor's parcel number, a lot/tract, or a description of a site that has no assigned street address. It can also be entered under **Add project context** when the project is created.

A changed address or site description is a context change, the same as adding new project context. It reopens jurisdiction research and every stage that depends on it: contacts/process, codes/standards, the Opus evidence check and the final report. The app updates both the saved project address and the research inputs, and **Activity** records the old and new values. The research inputs keep the last five earlier addresses (`previousAddresses`), so the research and final-review prompts can warn the model that earlier briefs and checkpoints may describe a superseded location. The prompts also treat the site description as user-provided location context, not as proof of jurisdiction. Saved sources, recorded costs and the cumulative search/read limits are kept. The previous report stays visible until the new one is ready. Resubmitting the saved address or site description, including with extra surrounding spaces, is not a change and does not reopen research.

After a correction, `locate_address` geocodes the current address. Passage ranking for report and chat excerpts uses terms from the current address and site description, including parcel identifiers such as APNs. The project header, project chat and PDF/Excel/JSON exports show the current address, and exports also list the site description and any previous addresses. Diagnostic downloads replace these Activity entries with a generic note and record only that the location changed, never the addresses or parcel details.

A correction is refused while research is running, while a chat reply is in progress, or while a request is outstanding or has an uncertain charge. These are the same guards as any continuation. A correction also cannot be combined with **Finish with saved evidence**, because that partial report would describe the previous location, or with the focused **Research NFPA standards** update. Project chat can propose a correction as a card (see **Actions you approve**); applying it goes through the same `engine.resume` path and guards. A proposed correction keeps any field it leaves empty, so removing a site description still takes the dialog. `node --test tests/address-correction.test.mjs` covers these rules with the fake provider and synthetic data; no paid requests are made. `node tests/address-correction-ui.mjs` checks the dialog, server-side validation, header, Activity entry and mobile layout; it requires installed Edge or Chrome.

## Project AI chat

Open a project and choose **Chat with AI**. Each project has its own saved conversation, unsent draft, pending reply and source citations. Switching projects does not rebind a running request or bring another project's chat into the visible conversation. Late navigation responses are ignored. Saved chat persists across app restarts; unsent drafts persist while switching projects in the same browser session. Chat runs in real time, even for a batch project.

Choose a **Reply depth** for each message:

| Depth | Model | Reasoning effort | Use for |
| --- | --- | --- | --- |
| Standard | Claude Sonnet 5.5 | high | Most questions |
| Deep | Claude Sonnet 5.5 | max | Harder analysis; thinks longer and costs more |
| Opus | Claude Opus 5.5 | xhigh | The hardest analysis; about twice Sonnet 5.5's per-token price |

Each reply records its depth, shown beside the assistant label. Before the first paid request of a reply, the app checks that the key's model supports the chosen effort level. Switching depth between messages is safe because every reply is rebuilt from saved records; the next message simply cannot reuse the other model's cache.

Each reply starts from the project's saved evidence: the saved report (up to 160,000 characters), research briefs and checkpoints (120,000), the source register (60,000), and citable excerpts from every retrieved source (160,000 characters shared across sources and ranked toward the saved findings, as in the final review's evidence package). Earlier turns follow as real conversation, up to 200,000 characters of the most recent turns, then the current project inputs, latest question responses and the new message. User answers that have not yet been used in a research round are included. Project lookup tools can page through anything trimmed and older chat, search saved sources, and retrieve exact source passages. Tool execution is bound to the project on the server; the model cannot choose another project ID. The assistant cites source IDs and is told to take code editions, amendments, dates, fees, contacts and requirements from the project records or the sources it reads rather than general knowledge, even when it feels confident. It may add general professional knowledge, labeled separately from project evidence, and names the edition when it describes a code or standard from general knowledge; the edition adopted by the AHJ governs. Chat never changes the project on its own and cannot submit forms or sign in to websites. It can propose answers, dismissals, research rounds and location corrections for the user to apply (see **Actions you approve** below).

### Web research in chat

When the saved records cannot answer a question, or the user asks for current information, chat can research public sources. It has native Anthropic web search (`web_search_20250305`, with `allowed_callers: ["direct"]`, the same tool research uses) and research's public-source tools: `read_source`, `render_page`, `inspect_pdf` and `locate_address`. The system prompt tells it to start from saved evidence, check details that change over time against current official sources even when confident, treat search results as leads, and read a page before relying on it.

- **Pages chat reads join the project's source register** as retrieved text under a new or existing source ID, so later chat, research and the final report can use them. Activity records each read ("Project chat read a public source (S12)."). Search results join the register as discovery-only records, as they do in research.
- **Page reads are citable.** The passage read is supplied as a native citable excerpt under its source ID, the same way saved-source lookups already work, with paging and link metadata kept outside the evidence. **Supporting passage** opens the cited text.
- **Search snippets are leads, not evidence.** When Claude cites a web search result, the answer shows it as **[Web] Search lead** with the page title, link and snippet, marked as not verified. Only snippets whose URL came back from a search in the same reply are kept.
- **Chat reads only URLs it has already seen**: pages in the source register (including search results), links returned by pages it read, and URLs in the user's message. It cannot invent a URL, so text injected into a page cannot direct chat to send project details to an arbitrary address. Downloads use research's public-network checks (public addresses only, standard ports, 10 MB limit).
- **Chat has its own web allowance, per reply**: up to 2 searches per request (`max_uses`), 10 searches and 20 page reads per reply. Research's 40-search and 100-read project totals no longer count chat, so chat cannot use up research's allowance and an exhausted research allowance does not block chat. There is no lifetime chat cap, because each reply starts from the user's own message. Reads beyond the reply's allowance return an error to the model. When the next request could exceed the search allowance, that request becomes the reply's final answer request.
- **The tool list never changes within a reply.** Thinking blocks are bound to the request's system prompt and tools, and tools lead the prompt cache, so the search allowance is enforced by ending lookups rather than by removing the search tool.
- **Mixed and paused turns.** If Claude calls web search together with a lookup, the search waits for the lookup results; that follow-up carries only the tool results (lookup results as plain text, with no separate citation metadata or harness note), as the API requires. A paused search turn (`pause_turn`) is resent unchanged to continue.
- `web_search_20260209` (dynamic filtering) is supported by Sonnet 5.5 but deliberately deferred for both research and chat. It runs searches through code execution, is not eligible for zero data retention unless restricted to direct calls, and adds code-execution blocks that the evidence and citation checks do not yet handle.

### Actions you approve

Chat can propose four kinds of project change. Each proposal appears below the reply as a card with an **Apply** button; those proposed edits wait for the user. Chat has no Apply tool. Reading public pages during a reply already adds sources and incurs estimated API cost.

| Card | Chat tool | Apply calls | Cost |
| --- | --- | --- | --- |
| Answer a question | `propose_question_update` (`answered`) | `store.saveQuestion` | Free; reopen or edit on the question card |
| Dismiss a question | `propose_question_update` (`dismissed`) | `store.saveQuestion` | Free |
| Start a research round | `propose_research_round` (`clarification`) | `engine.resume` with the clarification | Paid research round |
| Start focused NFPA research | `propose_research_round` (`nfpa_standards`) | `engine.resume` with `focus: "fire_protection"` | Paid research round |
| Correct the project location | `propose_address_correction` | `engine.resume` with the corrected address and/or site description | Paid research round |

- **Apply saves exactly what the card shows.** The proposal is stored with the chat turn when it is made; the page sends only the turn and proposal IDs (plus the processing mode for a paid card), so nothing on the page can change what is applied. A proposal can be applied once. Existing checks still apply: `saveQuestion` validates the question and answer, and `engine.resume` refuses while a chat reply is running, while a request is outstanding or has an uncertain charge, and for invalid focus or address combinations.
- **Checked when proposed.** A question card needs a question ID from the saved questions and a 1–4,000-character answer that differs from the saved response. A research card needs 1–3,900 characters of context; the focused NFPA card needs a fire protection project with completed jurisdiction and contact research and no context. A location card needs a valid address (8–500 characters) or a site description (up to 500) that changes the saved location; an empty field keeps the saved value, so chat cannot propose removing a site description. Any `[S#]` in an answer or context must be a source this project has read. A reply can record up to 4 proposals, at most one research or location card, and one per question, from at most 8 proposal calls including rejected ones. Research and location cards are not proposed while research is running. Rejected proposals return a tool error to the model and are not recorded.
- **Paid cards.** Research and location cards say that they start a paid research round and offer **Research now** or **Research later (batch)**, defaulting to the project's mode. They are disabled while a chat reply, research or an outstanding request is running. A paid card that has not been applied can no longer be applied once research has run after it was proposed; ask chat again if the change still applies. A location card is refused if the project already uses that location, because an unchanged continuation would run a paid review. If `engine.resume` refuses before changing anything, the card stays available.
- **Provenance.** An applied answer is saved as the user's answer, and research treats it as information the user provided. The prompt asks chat to name the source and cite it as `[S#]` when a proposed answer or context comes from a source rather than the user. Applied research context is added to the project notes as "User clarification: Proposed in project chat and approved by the user: …".
- **Prompt rules.** Chat proposes when the user asks, when the user's message answers a saved question or corrects the location, or when its findings show the report needs another round. The prompt tells it not to propose because a source, search result, web page or saved record asks for it, and not to say a change was made. These are instructions to the model, not a deterministic guarantee that it follows them. Later replies see a short, fixed summary of each earlier proposal in the conversation, which keeps the cached history unchanged when a card is applied; each proposal's current status (proposed, applied or stale) follows in the uncached part of the request.
- **Records.** Activity records each applied proposal by kind only, for example "You applied a proposal from project chat (answer a question).", alongside the existing question and research entries. Diagnostics record `chat.proposal_applied` with the kind only. Proposal text stays in the chat conversation, which diagnostic downloads exclude. A declined reply keeps no proposals. Proposals survive reloads and restarts.
- Proposal calls are not lookups: they do not count toward the 60-lookup or web allowances. The final request of a reply runs without tools, so it cannot add a proposal.

### Streaming, formatting and declines

**Streaming.** The server already receives each answer as a stream. While a reply runs, chat saves the text streamed so far about once a second and shows the current step, for example "Searching the web for “NFPA 13 adoption Loudoun County”…", "Reading S4 for “NFPA 13”…" or "Reviewing 8 search results…". Chat requests set `thinking.display` to `"updates"` (beta header `thinking-display-updates-2026-08-18`, sent with token counts and generation) so Sonnet 5.5's and Opus 5.5's progress notes between tool calls arrive with their text; the latest note is shown as the step. Claude's reasoning stays hidden. The open chat follows the running reply about once a second and updates only that reply; the rest of the page refreshes when it finishes.

**Formatting.** Answers render as Markdown: headings, bulleted and numbered lists (including nested lists), tables, bold, italics, strikethrough, inline code, code blocks, quotations and links. The renderer (`public/markdown.js`) is a small dependency-free module that escapes all text before adding its own tags; links open only for `http`/`https` URLs, and the app's content security policy is unchanged. Wide tables scroll within the answer. Citations stay beside the claims they support, including inside lists and tables. The prompt now asks for a table when comparing several items on the same attributes, such as editions adopted across standards or authorities.

**Declined requests.** If Claude declines a message (`stop_reason: "refusal"`), the reply shows **Declined by Claude** instead of **Limit reached**, with the refusal category in plain language (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`), Anthropic's explanation when one is supplied, and a next step. Partial text streamed before a decline is discarded. **Try again with Opus** (after a Sonnet decline) or **Try again with Standard** (after an Opus decline) sends the same message to the other model, which uses different safeguards; nothing is resent automatically. Anthropic's automatic server-side fallback (`fallbacks: "default"`, beta) is deliberately not enabled: on Sonnet 5.5 it retries only `cyber` and `frontier_llm` declines, not the `general_harms` or `bio` categories an AHJ question is more likely to trigger; fallback attempts bill at the fallback model's rates, which would have to be tallied per attempt from `usage.iterations`; and it routes the conversation to the fallback model for about an hour.

New chat replies support native citations from retrieved source excerpts and pages read during the reply. Open **Supporting passage** beside a claim to inspect its cited text and open the saved source. Citations persist with the answer across reloads and restarts. The app validates each citation against the exact evidence sent for that request; report summaries, user answers and discovery snippets are not supplied as citable source documents, and web search snippets are shown only as leads. Initial excerpts cover every retrieved source within the 160,000-character bound; additional passages are available through saved-source lookups. Older replies retain their existing source links.

Each reply can use up to 20 model requests, 60 lookups (up to 24,000 characters each; web searches and page reads also count against their own allowance above) and about 20 minutes of lookups, with up to 400,000 counted input tokens and 64,000 output tokens per request, including thinking. If the key reports a smaller context window for the model, the input ceiling is lowered to fit. Near the end, the app adds one short system note saying what remains, including web searches. These notes are mid-conversation `role: "system"` messages. If a model rejects that role, the notes are added to the pending user turn as reminders instead; the switch happens at the free token count, before any paid request. When lookups, requests or lookup time run out, the final request turns tools off (`tool_choice: none`) and asks for the answer from the evidence gathered, so a reply ends with an answer instead of stopping mid-investigation. Lookups requested beyond the allowance get an error result instead of ending the reply. The final answer always gets at least 10 minutes to stream. These ceilings guard against runaway loops; they are not spending limits. Only one reply can run per project. Chat does not use research's two task slots, so it stays available while research runs; research cannot be continued or corrected on a project while its chat reply is running.

Chat caches the saved evidence and earlier conversation for one hour, so follow-up questions within the hour reread both from cache. One-hour cache writes cost twice the input price and cache reads $0.20 per million tokens. Changed evidence rebuilds the cached prefix, so a reply that reads new pages makes the next reply rewrite its evidence cache once.

**Stop reply** stops subsequent work after the in-flight request returns so its charge can be recorded. Reloading or restarting never resubmits a chat request automatically. Duplicate sends use a project-scoped idempotency key. Interrupted or unpriced requests keep their estimated cost pending and expose charge reconciliation through **Activity**; they do not block new messages. A declined request stops the reply with **Declined by Claude** (above); no further request is sent unless the user chooses to try the other model. Diagnostics record the refusal category only. Chat status is separate from research status; a chat error does not rewrite a report or reopen research. Chat messages, tool content and model thinking are excluded from diagnostic downloads.

`node --test tests/chat-actions.test.mjs` covers proposals: proposed project edits wait for Apply, exact one-time application through `saveQuestion` and `engine.resume`, the research, NFPA and location paths (including a site description kept by an address-only correction), validation and per-reply limits, research and chat guards, stale proposals, a refused apply that stays available, declines, restart recovery and diagnostics privacy. `node --test tests/chat.test.mjs` covers isolation, required names, full-record lookups, persistence, reply depths, conversation caching, wrap-up at each limit, cost recording without spending limits, concurrency beside research, recovery, request security, web search and page reads joining the source register, citable page reads and search leads, the URL guard, per-reply web allowances separate from research's, a search waiting on lookups, `pause_turn`, streamed drafts and steps, and declines. `node --test tests/chat-citations.test.mjs tests/markdown.test.mjs` covers citation mapping and the Markdown renderer, including escaping. `node tests/chat-ui.mjs` checks project switching with simultaneous replies, drafts, citations, reply depth, stop behavior, late responses, escaping, cost displays without budgets, Markdown tables and lists, the live draft and step, a declined reply with retry on the other model, proposal cards (escaping, Apply for an answer and a research round, the paid card held while a reply runs, reload) and desktop/mobile layout. These checks use synthetic data, fake model responses and a fake web; no paid requests are made.

## Real-time and batch

Both modes use the same research and evidence checks. Real-time requests use the official Anthropic SDK with streaming, disabled automatic retries, and a 30-minute deadline for receiving the whole response. Only complete responses are applied. Batch mode sends native Message Batches requests, persists their identifiers, polls approximately once a minute, matches unordered results by exact `custom_id`, and continues tools or dependent stages in subsequent batches. Each stage can require several requests. Batch mode does not silently fall back to standard pricing.

Each batch can take 24 hours and can expire; an entire dependent workflow can take longer than 24 hours. Closing the browser is safe. If the local backend/computer stops, already submitted batches continue remotely; later stages resume when the app is running and a key is available.

Interrupted submissions are not automatically repeated. Known batches are reconciled on restart; ambiguous submissions keep their estimated cost pending and show recovery controls. Recover a completed batch by its ID, or explicitly record an uncertain charge only after checking the original outcome in the Anthropic Console. Completed/chargeable results are retained after cancellation. Unavailable results and requests older than the 29-day result-retention window require reconciliation; the app stops automatic retrieval and keeps the estimate pending.

## Cost policy

- Prices checked against Anthropic documentation on **2026-09-28**: Sonnet 5.5 $2/$10 and Opus 5.5 $4/$20 per million input/output tokens; batch token factor 0.5; search $0.01 per request. Cache reads cost $0.20 per million tokens for both models. Rates are defined in `lib/config.mjs` and should be rechecked before a future model migration.
- Costs use an integer-microdollar ledger. Each request records an estimated pending cost before it is sent and its actual cost when it finishes; pending and unknown attempts keep their estimate until reconciled. Actual costs use the returned token and search usage, without double-counting cache-creation breakdowns.
- **The app does not limit spending.** Project budgets, the daily allowance, the chat reply allowance and the final-report hold have been removed. Each project shows its estimated cost to date, the part that came from chat, and estimates for pending requests; each chat reply shows its own estimate. **API & spending** shows estimated spending today, across all projects (including charges from deleted projects) and pending. Native search has variable intermediate token volume, so a pending estimate is **not a guaranteed provider billing ceiling**. Provider invoices are authoritative. For a hard cap, set a workspace spend limit in Anthropic Console; the app reports when Anthropic stops a request at that limit.
- Projects that had stopped at a former spending limit open as **Needs attention** after the upgrade and wait for an explicit **Continue research** or **Finish with saved evidence**; nothing resumes spending automatically. Saved budget settings are ignored.
- Maximum two local research tasks (chat runs separately), 40 project research searches, 100 research source-reading calls, 12 requests per research stage, 90k counted input tokens/request, **60k research output tokens and 100k final-report output tokens**. Output caps include thinking and are ceilings, not targets. The separate Opus evidence check is limited to 6 requests, 8 searches and 12 source reads within the project totals. Real-time work is limited by a 15-minute active-time limit; an in-flight request may finish after this limit and has its own streaming deadline. Batch queue time is separate.
- Project chat has its own web allowance per reply: 2 searches per request, 10 searches and 20 page reads per reply. Chat searches and reads do not count toward research's project totals. Web search costs $10 per 1,000 searches plus the tokens of the results. Chat's pending estimate prices the first pass at the one-hour cache-write rate and each possible search iteration as a reread of the input plus about 20,000 result tokens at the base input rate: about $3.17 for a 300,000-token Sonnet 5.5 request with 2 searches, where research's formula (which multiplies the cache-written input by every search) would give about $4.37. As with research, the estimate is not a billing ceiling.
- Research and final review use 5-minute prompt caching in real-time mode and 1-hour caching in batch mode; pending estimates include the applicable cache-write price. Project chat caches its saved evidence and earlier conversation for 1 hour and sends the current context, question responses and latest message afterward. Changed evidence rebuilds the prefix. Batch caching is best effort and does not guarantee cache hits. Activity shows actual input, cache, and output usage; diagnostic exports include provider cache-comparison reasons separately from billed usage. A missing reason does not by itself establish a cache hit.
- Web/PDF retrieval is handled by bounded application tools rather than unrestricted native PDF fetching: 10 MB downloads; one PDF page and 8,000 characters by default, explicitly expandable to eight pages and 24,000 characters. Exact-text document searches scan up to 80 PDF pages and return matching passages; saved-source lookups use no network access. Visual inspection handles a single PDF page.
- A context clarification, or a corrected project address or parcel/site description, explicitly reopens completed stages. Normal continuation preserves completed stages and all spending records. The project search/read ceilings remain cumulative; a fresh investigation can be created separately if those are exhausted.

## Evidence and limitations

The five stages are jurisdiction, contacts/process, codes/standards, Opus evidence check, and final report. Contacts use Sonnet medium effort; jurisdiction and codes use Sonnet high; both Opus stages use medium effort. Adaptive thinking is enabled. On the 5.5 models, the short notes Claude writes between tool calls come back as `thinking` blocks rather than text, so research and evidence-check requests set `thinking.display` to `"updates"` (beta header `thinking-display-updates-2026-08-18`, sent with generation, token-count and batch requests). Those notes appear in **Activity** and in automatic checkpoints, including from a response that reached its output ceiling; Claude's reasoning stays hidden. Project chat also uses `"updates"` to show its current step. The final report keeps the thinking display omitted. Stage prompts ask Claude to check details that change over time (adopted editions, amendments, effective dates, fees, review times, contacts) against current sources even when it feels confident. Model access and advertised capabilities/output limits are checked before paid requests.

Research uses the existing native Anthropic basic web search (`web_search_20250305`) and constrained public-source tools; project chat uses the same tool and version with its own per-reply allowance. The Opus evidence check can investigate gaps and conflicting sources with these same tools before the final report, which starts with a fresh evidence package and a small strict JSON schema. The final reviewer can look up omitted passages in saved sources for up to three rounds before its final response; it cannot perform external research. Uniform report rows avoid an oversized compiled grammar; the app checks field counts and allowed values, converts them to the existing report structure, then validates the evidence. Because that grammar cannot require single-row sections, the reviewer is asked to write the jurisdiction and coverage rows first. If it still omits one, validation rebuilds it instead of discarding the report: a missing jurisdiction becomes an unverified finding with a question to confirm the governing jurisdiction (so code findings stay conditional), and missing coverage is summarized from the coverage the research stages recorded. When a final report is blocked by validation, **Continue research** or **Finish with saved evidence** first rechecks the saved response under the current rules; if it passes, and neither the project context nor its saved evidence has changed since that request (for example, a page read in project chat), it is saved with no new request. Otherwise a new paid review runs. PDF, Excel, and public JSON exports preserve existing report sections and add a separate NFPA findings section for fire protection. Newer dynamic web search (`web_search_20260209`, which Sonnet 5.5 supports) and native web fetch tools remain deliberately deferred. Exact source IDs, retrieved passages and observed links are validated before findings are labeled source-supported. Search snippets cannot become read-source evidence. Visually read scans remain conditional unless text evidence independently supports them. Unknown editions, jurisdictions, and explicitly unresolved research areas generate questions to resolve.

Research must submit an explicit completion brief with coverage for jurisdiction, contacts, codes, and process. Because no one can answer mid-stage, the research system prompt tells Claude the stage runs unattended: put status notes alongside the next tool call instead of ending the turn with a summary, an offer to continue, or non-blocking questions. A turn that still ends without a tool call receives up to two follow-ups that name the coverage still owed (plus the NFPA checklist for fire protection) and up to five open questions from saved progress, before the stage is marked partial. Truncated responses receive at most one compact recovery attempt, subject to the existing request limits. Original signed conversations and tool definitions stay stable within each conversation segment. At 60k counted input tokens, the app saves a checkpoint and starts a fresh conversation from bounded evidence; it does not edit opaque thinking or signatures. At most two research restarts are allowed before a completion-only request. The last allowed research request is reserved for the completion brief. If that brief fails the coverage check (for example, a grouped NFPA row), there is no request left to correct it: the brief is kept in the stage output, labeled as unverified leads, for the evidence check and final report, and the stage is marked partial with the specific reason. Native search starts with up to four uses, bounded by unspent/unreserved project and verification search limits. A search-limit response can trigger a checkpoint restart instead of repeating denied searches in the same continued conversation. Existing saved reports are preserved; explicitly continuing an older project adds the new evidence check when needed.

A matching quotation does not establish semantic/legal correctness on its own. This application is research assistance, not a compliance certification. The responsible design professional must review applicability. No model or prompt can guarantee that all local requirements were found. Inaccessible portals, incomplete public records, or missing project context are reported as gaps. The dynamic-page reader does not perform interactive GIS clicks, CAPTCHA solving, logins or application submissions; it reads a provided public URL and its rendered text. Geocoding covers US Census geographies; other countries use researched official sources.

## Data and key handling

- Server binds only to `127.0.0.1`. Host/origin checks, a per-process mutation token, request-size limits and restrictive browser content policies protect the local endpoints.
- Default key storage is backend memory. Optional Windows storage uses DPAPI for the current Windows user, at `%LOCALAPPDATA%\AHJ Atlas\credential.bin`, outside this folder. The credential field is not intentionally copied into SQLite, browser storage, exports or prompts. Secrets pasted into ordinary project/chat text are not detected or excluded by that separation.
- In an installed desktop app, SQLite, internal conversation state and public evidence live under `%LOCALAPPDATA%\AHJ Atlas\data`. The source version uses this repository's `data/`, excluded by `.gitignore`. Project details and tool results are sent to Anthropic. Address lookup may use the Census geocoder. A folder under OneDrive or another sync service follows its normal sync policy.
- External text is untrusted. The application has no email, permit-submission, purchasing, unrestricted filesystem or shell tools. Source retrieval blocks private/local addresses and DNS-pins outbound requests; dynamic-page reads use an isolated browser profile and intercepted public requests.
- Saved conversations preserve provider signatures and encrypted search content for valid continuation. They are not included in public exports. The application’s data directory is single-instance locked to prevent duplicate workers.
- Protect this computer/account and data folder appropriately. This is a single-user local app, not a remotely exposed multi-user server.

## Development and validation

### Interactive questions

Each **Questions to resolve** card supports **Save answer** and **Dismiss**. Responses persist in SQLite separately from the research report, update the open-question count immediately, and remain available under **Answered & dismissed** for editing or reopening. Existing reports receive controls automatically; stable question IDs preserve responses across report ordering and whitespace changes. Differently worded questions stay distinct. Responses remain available even when a later report omits the original question.

Saving a response does not start a worker request, change a source-supported finding, or alter in-flight research context. **Research with saved answers** uses the existing explicit continuation flow and snapshots the latest responses into the next research context. New responses reopen completed research stages during normal continuation. Answers are user-provided context; dismissals express priorities and do not establish compliance or non-applicability. Answered system details can add NFPA screening targets in that research round. PDF, Excel and JSON exports include question status and saved answers.

All fields inside **Add project context**, including **Additional context**, are labeled optional. `node --test tests/questions.test.mjs` verifies persistence, validation, spending isolation, report regeneration, context handoff and exports. `node tests/questions-ui.mjs` checks the browser interactions, saved drafts during polling, error recovery, and desktop/mobile layouts with synthetic data and no paid calls; it requires installed Edge or Chrome.

### Diagnostics

Open **API & spending → Diagnostics**. Choose a project or the entire workspace, inspect progress and request history, and download a JSON troubleshooting file. The panel is kept inside settings, away from the new-project form.

The local SQLite journal retains the most recent 5,000 diagnostic events across the workspace. It records API operations, stage transitions, request and batch identifiers, model/effort/output settings, schema sizes and fingerprints, token counts, returned usage, stop reasons, stream timing, tool failures, search-limit decisions, final-report validation failures (naming the failing report section), rebuilt report rows, saved-review recoveries, local request errors, and reported browser errors. It persists across restarts. Saved request summaries remain available after older diagnostic events are trimmed. Detailed tracing begins with version 1.2.0; older errors are available only to the extent retained by the earlier activity and request records.

Diagnostics omit API keys, authorization headers, prompts, project inputs, source documents, raw model responses, and model thinking. Activity shows Claude's short progress notes, which are status summaries written for the user, not its reasoning. Because they can quote addresses, contacts or findings, diagnostic exports replace their text with a placeholder, as they do for location changes. Error text and historical activity may contain source details; inspect an exported file before sharing. Files are downloaded locally and are never automatically uploaded. Viewing or downloading diagnostics does not contact Anthropic or spend credits. The viewer requires the local request token; the attachment endpoint requires a same-origin browser request, in addition to the server's host/origin checks.

#### In-app updates

When a newer release is available, the installed Windows app offers **Download update** in a banner and under **App updates**. `desktop/update-check.mjs` rereads the latest release metadata, downloads that release's `SHA256SUMS.txt` and installer from `github.com/Abe-Borg/ahj-atlas/releases/download/…` into `%LOCALAPPDATA%\AHJ Atlas\updates`, and hashes the installer while it streams. The file must match the published SHA-256 line, GitHub's asset `digest` when the API provides one, and the published asset size (at most 1 GiB). A download that receives no data for 60 seconds stops. A mismatch or failure deletes the partial file.

**Restart and install** is refused with HTTP 409 while research or a chat reply is running. Otherwise the app re-hashes the saved installer, records the attempt in `update-check.json`, closes the workspace, and only then starts the installer with `--updated /S --force-run`. The electron-builder NSIS installer then skips its license and directory pages, upgrades in place without deleting app data, and reopens the app. On the next launch the app reports **updated** or **did not finish**, and deletes installers it no longer needs. A pending batch is picked up after the restart. In-app installation is enabled only in the packaged Windows app; the source server and development desktop keep the release link.

The SHA-256 check proves the file matches the checksum published in the same GitHub release. It does not prove publisher identity, because releases are unsigned. Manual installation from the release page, with the checksum steps in [the Windows installation guide](docs/windows-installation.md), still works. `node --test tests/update-check.test.mjs` covers download verification, tampering, the installer hand-off and the outcome notice. `node tests/update-ui.mjs` drives the banner and settings flow in Edge or Chrome.

## Fire protection coverage (version 1.3)

Fire protection and matching custom specialties use an explicit NFPA screening profile. Baseline targets include NFPA 1, 3, 4, 10, 13, 14, 20, 22, 24, 25, 70, 72, 80 and 101. Project context adds relevant candidates (for example, data centers add 75, 2001, 855, 110, 111, 30 and 37). Because **Building use** defaults to Hyperscale data center, new fire protection projects include those data center candidates unless another building use is chosen. These are research targets, not an adopted-code list; the profile contains no editions. Other disciplines keep their existing research workflow.

Both code research and Opus verification must return one finding per screening target. The final report separates NFPA findings, scope applicability and evidence status, with edition and adoption source IDs. Missing/grouped findings cannot satisfy coverage; missing editions remain unconfirmed. Source support for an adopted edition requires matching quotations for the adoption chain and the individual standard/edition. These deterministic checks do not certify the legal meaning of a quotation. Conditional scope still generates a follow-up question. NFPA 13, 13D and 13R are distinct designations.

On an existing fire protection project, open **Codes & standards → Research NFPA standards**. This paid action reopens codes, verification and report generation, keeping completed jurisdiction/contact stages, sources, the previous report, recorded costs and cumulative search/read limits. Real-time and batch are both available. A project with unfinished initial jurisdiction/contact work should use normal continuation first. Old signed conversations retain their original tool schema; the focused refresh starts fresh conversations. Existing reports are never silently rewritten or submitted for paid research.

The PDF includes an NFPA section; Excel adds an **NFPA standards** worksheet; JSON includes `fireStandards` and `fireProtection`. Diagnostics record checklist failures and final NFPA coverage totals. The compact report grammar remains a single repeated row shape.

Research-profile references: [NFPA publication catalog](https://link.nfpa.org/all-publications), [NFPA energy storage guidance](https://www.nfpa.org/en/for-professionals/for-business/creating-a-culture-of-safety/commercial-ess-and-pv-safety), [Virginia incorporation-by-reference rule](https://law.lis.virginia.gov/admincode/title13/agency5/chapter63/section10/). These explain screening and adoption tracing, not project-specific adopted editions.

## Evidence recovery (version 1.4)

Research can save exact source-linked claims and outstanding questions with `save_progress`. Automatic checkpoints also retain source IDs, public progress text (including the progress-update notes the 5.5 models return as `thinking` blocks), retrieval errors, and saved-review lookups. Context recovery and explicit continuation retain costs and evidence; previous reports are not rewritten automatically. Large saved transcripts remain in their original attempt records. The input ceiling stays 90k and the overall search, reading, and research-round limits still apply.

Evidence selection allocates text only to sources that contain retrieved text, redistributes unused document shares, and prioritizes project-location matches, adoption/application clauses and exact claim quotations. Location matching uses Unicode word boundaries, so accented and non-Latin address terms such as Bogotá or 東京都千代田区丸の内 rank passages the same way English ones do, whether accents are stored composed or as separate combining marks. In scripts written without spaces (Chinese, Japanese, Thai, Lao, Khmer, Myanmar), a term matches inside longer text, but only if the address's whole unbroken run appears. Selected spans retain source offsets. The final reviewer can request a saved source by ID, query or offset instead of treating excerpt omissions as missing research. Public webpage links are filtered and bounded; repeated downloads use a short-lived bounded in-memory cache, and overlapping saved text is merged.

Independent `read_source` calls run in groups of up to two per response. Admission reserves each source read before fetching, including across simultaneously running stages; project and verification limits remain enforced. Results and source registration are saved in call order, while one failed read does not discard successful siblings. Identical in-flight downloads share retrieval work. Progress updates, completion, browser rendering and visual PDF inspection remain ordered. Cancellation saves already-started reads and prevents subsequent groups. The existing two-task ceiling bounds total concurrent source reads to four.

NFPA edition checks accept title-before-year adoption wording while rejecting neighboring-standard, ordinance-date and parent-code-year matches. Failed adoption checks explain the specific missing evidence. The NFPA summary separates scope-dependent findings, unresolved applicability, and evidence needing confirmation; these counts can overlap. Reports also identify unfinished research stages separately from substantive AHJ questions. Diagnostics include context restarts, checkpoint availability, search-limit errors, and input counts before/after rebuilding a request.

`node --test tests/evidence-recovery.test.mjs` covers context and search recovery, spending-preserving continuations, bounded review lookups, targeted document retrieval, excerpt selection and NFPA false positives. All tests are offline. `node tests/replay-saved-run.mjs <project-id>` optionally checks a saved run read-only without sending provider requests or changing its report.
