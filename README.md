# AHJ Atlas

A local HTML/CSS/JavaScript application for source-linked AHJ, professional contact, code-adoption, and submission research. The Windows desktop build includes its own Electron/Node runtime; source development uses Node.js 24. No hosting subscription is required.

## Windows installer

Download the unsigned, per-user Windows x64 installer and its checksum from a [published GitHub Release](https://github.com/Abe-Borg/ahj-atlas/releases). Follow the [Windows installation guide](docs/windows-installation.md) for checksum verification, the unsigned publisher warning, installation, upgrades, backup, and removal. The installed app includes its runtime; installed users do not need Node.js, `npm`, or the `.cmd` launchers.

Research and chat require internet access and an Anthropic API key. Ordinary search and source reading do not require Edge or Chrome. The optional JavaScript page renderer currently uses an installed Edge or Chrome browser.

## Source development

Source development requires Node.js 24 or newer. Run `npm ci` in this checkout, then use `npm start` to keep the local backend in a terminal. On Windows, **Start AHJ Atlas.cmd** starts a hidden backend at http://127.0.0.1:4318 and opens the system browser; **Stop AHJ Atlas.cmd** drains in-flight work and stops it. Closing only the browser leaves that source backend running. These launchers are for source users, not installed-app users.

In **API & spending**, enter an Anthropic API key with access to `claude-sonnet-5-5` and `claude-opus-5-5` for new work. Enable web search in the Anthropic Console. The connection checks the key through Anthropic's Models API; each request checks access and capabilities for its actual model before a paid response is generated. An in-progress Sonnet 5 conversation can continue with a key that still has access to its original model. A Chat subscription does not replace API access.

The sidebar connection button shows **Claude connected** only after Anthropic accepts the key. It shows **Claude disconnected** when no key is entered or when Anthropic rejects the key. A remembered key is checked again each time the app starts. While the app runs, any request Anthropic rejects as unauthorized (for example, a revoked key) also switches the button to **Claude disconnected**. **Checking Claude…** appears briefly while a remembered key is being checked. **Claude unreachable** means the key could not be checked because Anthropic could not be reached; the app checks again about once a minute while it is open. Hover over the button, or open **API & spending**, to see the reason. New projects created while the key is missing or rejected wait for a working key. `node --test tests/provider.test.mjs` covers these states, and `node tests/connection-ui.mjs` checks the button in a browser without a real key.

Enter the required project name, address and discipline, optional scope/occupancy/permit date, processing mode, and spending allowance. Choose **Other — enter your discipline** for a specialty not listed. The report includes authorities, professional contacts, adopted editions, local amendments, permit requirements, source passages, and unresolved questions. PDF, native XLSX, and JSON exports are supported even for partial research.

To remove a project, open it and choose **Delete project**, then confirm. This permanently removes its saved report, sources, answers, and chat history; export anything you want to keep first. Stop active research or chat and let outstanding requests finish before deleting. Uncertain charges must be resolved in **Activity**. Recorded charges still count toward the daily allowance.

## Project AI chat (version 1.5)

Open a project and choose **Chat with AI**. Chat uses **Claude Sonnet 5.5 at high effort**, in real time even for a batch project. Each project has its own saved conversation, unsent draft, pending reply and source citations. Switching projects does not rebind a running request or bring another project's chat into the visible conversation. Late navigation responses are ignored. Saved chat persists across app restarts; unsent drafts persist while switching projects in the same browser session.

Each reply gets the latest project context, including user answers that have not yet been used in a research round. Bounded previews include the report, inputs, question responses, research briefs/checkpoints and source register, plus recent conversation. Read-only tools can page through the full project records and older chat, search saved sources, and retrieve exact source passages. Tool execution is bound to the project on the server; the model cannot choose another project ID. The assistant uses saved evidence and cites source IDs. Fresh public-source investigation remains an explicit research action, and chat cannot edit the report or mark a question answered on the user's behalf.

New chat replies support native citations from retrieved source excerpts. Open **Supporting passage** beside a claim to inspect its cited text and open the saved source. Citations persist with the answer across reloads and restarts. The app validates each citation against the exact evidence sent for that request; report summaries, user answers and discovery snippets are not supplied as citable source documents. Initial excerpts are bounded to six sources and 12,000 characters; additional passages are available through saved-source lookups. Older replies retain their existing source links.

**Spending & limits** allows a reply allowance (default $1, range $0.25–$5) and a total project allowance. Chat shares the existing project/daily ledger and preserves the final-report hold. Each reply permits at most four model requests, eight saved-project lookups and five minutes, with 60,000 input tokens and 8,000 output tokens per request including thinking. Up to two local tasks can run across chat and research, and only one reply can run per project. Token counts and reservations are checked before each paid request. These are scheduling allowances, not guaranteed provider billing ceilings.

**Stop reply** stops subsequent work after the in-flight request returns so its charge can be recorded. Reloading or restarting never resubmits a chat request automatically. Duplicate sends use a project-scoped idempotency key. Interrupted or unpriced requests retain reservations and expose charge reconciliation through **Activity**. Chat status is separate from research status; a chat error does not rewrite a report or reopen research. Chat messages, tool content and model thinking are excluded from diagnostic downloads.

`node --test tests/chat.test.mjs` covers isolation, required names, full-record lookups, persistence, budgets, concurrency, recovery and request security. `node tests/chat-ui.mjs` checks project switching with simultaneous replies, drafts, citations, stop behavior, late responses, escaping and desktop/mobile layout. These checks use synthetic data and fake model responses; no paid requests are made.

## Real-time and batch

Both modes use the same research and evidence checks. Real-time requests use the official Anthropic SDK with streaming, disabled automatic retries, and a 30-minute deadline for receiving the whole response. Only complete responses are applied. Batch mode sends native Message Batches requests, persists their identifiers, polls approximately once a minute, matches unordered results by exact `custom_id`, and continues tools or dependent stages in subsequent batches. Each stage can require several requests. Batch mode does not silently fall back to standard pricing.

Each batch can take 24 hours and can expire; an entire dependent workflow can take longer than 24 hours. Closing the browser is safe. If the local backend/computer stops, already submitted batches continue remotely; later stages resume when the app is running and a key is available.

Interrupted submissions are not automatically repeated. Known batches are reconciled on restart; ambiguous submissions retain their allowance and show recovery controls. Recover a completed batch by its ID, or explicitly record an uncertain charge only after checking the original outcome in the Anthropic Console. Completed/chargeable results are retained after cancellation. Unavailable results and requests older than the 29-day result-retention window require reconciliation; the app stops automatic retrieval and retains the reservation.

## Cost policy

- Prices checked against Anthropic documentation on **2026-09-28**: Sonnet 5.5 $2/$10 and Opus 5.5 $4/$20 per million input/output tokens; batch token factor 0.5; search $0.01 per request. Cache reads cost $0.20 per million tokens for both models. Rates are defined in `lib/config.mjs` and should be rechecked before a future model migration.
- Project and daily allowances use an integer-microdollar ledger. Pending and unknown attempts keep reservations. Actual costs use the returned token and search usage, without double-counting cache-creation breakdowns.
- Native search has variable intermediate token volume. This is a scheduling guard, **not a guaranteed provider billing ceiling**. Input is counted before requests, output/search use is capped, and a final-report allowance is held across projects: currently $2.48 real-time or $1.39 batch, including the applicable cache-write price. Stopping a project releases its unused final-report hold; in-flight and uncertain requests retain their reservations. Provider invoices are authoritative.
- Maximum two local tasks, 40 project searches, 100 source-reading calls, 12 requests per research stage, 90k counted input tokens/request, **60k research output tokens and 100k final-report output tokens**. Output caps include thinking and are ceilings, not targets. The separate Opus evidence check is limited to 6 requests, 8 searches and 12 source reads within the project totals. Real-time work is limited by a 15-minute active-time allowance; an in-flight request may finish after this allowance and has its own streaming deadline. Batch queue time is separate.
- Research and final review use 5-minute prompt caching in real-time mode and 1-hour caching in batch mode; reservations include the applicable cache-write price. Project chat explicitly caches its saved report/evidence prefix for 5 minutes and sends current context, question responses, spending, history and the latest message afterward. Changed evidence rebuilds the prefix. Batch caching is best effort and does not guarantee cache hits. Activity shows actual input, cache, and output usage; diagnostic exports include provider cache-comparison reasons separately from billed usage. A missing reason does not by itself establish a cache hit.
- Web/PDF retrieval is handled by bounded application tools rather than unrestricted native PDF fetching: 10 MB downloads; one PDF page and 8,000 characters by default, explicitly expandable to eight pages and 24,000 characters. Exact-text document searches scan up to 80 PDF pages and return matching passages; saved-source lookups use no network access. Visual inspection handles a single PDF page.
- A context clarification explicitly reopens completed stages. Normal continuation preserves completed stages and all spending records. The project search/read ceilings remain cumulative; a fresh investigation can be created separately if those are exhausted.

## Evidence and limitations

The five stages are jurisdiction, contacts/process, codes/standards, Opus evidence check, and final report. Contacts use Sonnet medium effort; jurisdiction and codes use Sonnet high; both Opus stages use medium effort. Adaptive thinking is enabled. Model access and advertised capabilities/output limits are checked before paid requests.

Research uses the existing native Anthropic basic web search (`web_search_20250305`) and constrained public-source tools. The Opus evidence check can investigate gaps and conflicting sources with these same tools before the final report, which starts with a fresh evidence package and a small strict JSON schema. The final reviewer can look up omitted passages in saved sources for up to three rounds before its final response; it cannot perform external research. Uniform report rows avoid an oversized compiled grammar; the app checks field counts and allowed values, converts them to the existing report structure, then validates the evidence. PDF, Excel, and public JSON exports preserve existing report sections and add a separate NFPA findings section for fire protection. Newer dynamic web search and native web fetch tools remain deferred. Exact source IDs, retrieved passages and observed links are validated before findings are labeled source-supported. Search snippets cannot become read-source evidence. Visually read scans remain conditional unless text evidence independently supports them. Unknown editions, jurisdictions, and explicitly unresolved research areas generate questions to resolve.

Research must submit an explicit completion brief with coverage for jurisdiction, contacts, codes, and process. A progress-only response receives up to two follow-ups before the stage is marked partial. Truncated responses receive at most one compact recovery attempt, subject to the existing request and spending limits. Original signed conversations and tool definitions stay stable within each conversation segment. At 60k counted input tokens, the app saves a checkpoint and starts a fresh conversation from bounded evidence; it does not edit opaque thinking or signatures. At most two research restarts are allowed before a completion-only request. The last allowed research request is reserved for the completion brief. Native search starts with up to four uses, bounded by unspent/unreserved project and verification allowances. A search-limit response can trigger a checkpoint restart instead of repeating denied searches in the same continued conversation. Existing saved reports are preserved; explicitly continuing an older project adds the new evidence check when needed.

A matching quotation does not establish semantic/legal correctness on its own. This application is research assistance, not a compliance certification. The responsible design professional must review applicability. No model or prompt can guarantee that all local requirements were found. Inaccessible portals, incomplete public records, or missing project context are reported as gaps. The dynamic-page reader does not perform interactive GIS clicks, CAPTCHA solving, logins or application submissions; it reads a provided public URL and its rendered text. Geocoding covers US Census geographies; other countries use researched official sources.

## Data and key handling

- Server binds only to `127.0.0.1`. Host/origin checks, a per-process mutation token, request-size limits and restrictive browser content policies protect the local endpoints.
- Default key storage is backend memory. Optional Windows storage uses DPAPI for the current Windows user, at `%LOCALAPPDATA%\AHJ Atlas\credential.bin`, outside this folder. No API key is written to SQLite, browser storage, exports or prompts.
- In an installed desktop app, SQLite, internal conversation state and public evidence live under `%LOCALAPPDATA%\AHJ Atlas\data`. The source version uses this repository's `data/`, excluded by `.gitignore`. Project details and tool results are sent to Anthropic. Address lookup may use the Census geocoder. A folder under OneDrive or another sync service follows its normal sync policy.
- External text is untrusted. The application has no email, permit-submission, purchasing, unrestricted filesystem or shell tools. Source retrieval blocks private/local addresses and DNS-pins outbound requests; dynamic-page reads use an isolated browser profile and intercepted public requests.
- Saved conversations preserve provider signatures and encrypted search content for valid continuation. They are not included in public exports. The application’s data directory is single-instance locked to prevent duplicate workers.
- Protect this computer/account and data folder appropriately. This is a single-user local app, not a remotely exposed multi-user server.

## Development and validation

### Interactive questions

Each **Questions to resolve** card supports **Save answer** and **Dismiss**. Responses persist in SQLite separately from the research report, update the open-question count immediately, and remain available under **Answered & dismissed** for editing or reopening. Existing reports receive controls automatically; stable question IDs preserve responses across report ordering and whitespace changes. Differently worded questions stay distinct. Responses remain available even when a later report omits the original question.

Saving a response does not start a worker request, change a source-supported finding, or alter in-flight research context. **Research with saved answers** uses the existing explicit, budget-checked continuation flow and snapshots the latest responses into the next research context. New responses reopen completed research stages during normal continuation. Answers are user-provided context; dismissals express priorities and do not establish compliance or non-applicability. Answered system details can add NFPA screening targets in that research round. PDF, Excel and JSON exports include question status and saved answers.

All fields inside **Add project context**, including **Additional context**, are labeled optional. `node --test tests/questions.test.mjs` verifies persistence, validation, spending isolation, report regeneration, context handoff and exports. `node tests/questions-ui.mjs` checks the browser interactions, saved drafts during polling, error recovery, and desktop/mobile layouts with synthetic data and no paid calls; it requires installed Edge or Chrome.

### Diagnostics

Open **API & spending → Diagnostics**. Choose a project or the entire workspace, inspect progress and request history, and download a JSON troubleshooting file. The panel is kept inside settings, away from the new-project form.

The local SQLite journal retains the most recent 5,000 diagnostic events across the workspace. It records API operations, stage transitions, request and batch identifiers, model/effort/output settings, schema sizes and fingerprints, token counts, returned usage, stop reasons, stream timing, tool failures, budget decisions, local request errors, and reported browser errors. It persists across restarts. Saved request summaries remain available after older diagnostic events are trimmed. Detailed tracing begins with version 1.2.0; older errors are available only to the extent retained by the earlier activity and request records.

Diagnostics omit API keys, authorization headers, prompts, project inputs, source documents, raw model responses, and model thinking. Error text and historical activity may contain source details; inspect an exported file before sharing. Files are downloaded locally and are never automatically uploaded. Viewing or downloading diagnostics does not contact Anthropic or spend credits. The viewer requires the local request token; the attachment endpoint requires a same-origin browser request, in addition to the server's host/origin checks.

`npm test` runs deterministic fake-provider tests: real-time and multi-stage batch workflows, streaming contracts and interruption handling, model capability checks, billing/cache calculations, atomic reservations and shared final-report holds, midnight batch accounting, retry delays, duplicate submission/application prevention, cancellation races, saved-project migration, custom disciplines, source provenance, private-network blocking, request security, and native PDF/XLSX exports. No paid API calls are made by these tests.

Before relying on a release for project research, run a small, budgeted evaluation with an authorized API key: compare real-time and batch reports for an incorporated city, an unincorporated address, a jurisdiction with local amendments, and a custom discipline. Check authority boundaries, adoption/effective dates, contact currency, cited passages, unresolved gaps, actual cost, and time to completion against official records. Fake-provider tests establish application behavior, not model research quality or live account compatibility.

`npm run check` checks server/frontend syntax. `node tests/preview.mjs` starts an isolated synthetic UI test workspace on port 4319 with fake provider responses; it never uses the user’s key or makes paid API calls. Do not use its synthetic results for design.

### Electron development shell

`npm run desktop` opens the existing loopback application in a sandboxed Electron window. Source-mode runs use a separate temporary development profile and data directory. A packaged desktop run uses `%LOCALAPPDATA%\AHJ Atlas\data` for the workspace and the existing `%LOCALAPPDATA%\AHJ Atlas\credential.bin` DPAPI location. It offers a first-run import of a source installation's `data` folder before opening the workspace. `npm start` and the source launchers still work as before.

Desktop exports download into a private temporary file, then ask where to save with a native dialog. Existing files are never silently replaced; completion, cancellation and failures are announced. The server supplies sanitized PDF, XLSX, JSON and diagnostics filenames. Help stays in the app window, while public source and Anthropic links open in the default browser. The version shown in Diagnostics comes from `package.json`, the same metadata used by Electron. Installed builds check GitHub Releases for a newer published Windows installer at most once every 24 hours while the app is open; **API & spending → App updates** also offers a manual check. Installation remains a manual, checksum-verified step.

For a Windows x64 smoke test without paid requests, use a disposable directory and the fake provider:

```powershell
$env:ATLAS_DESKTOP_DATA_DIR = Join-Path (Get-Location) 'test-results\desktop-session-1'
$env:ATLAS_DESKTOP_PROFILE_DIR = Join-Path (Get-Location) 'test-results\desktop-profile-session-1'
npm run desktop -- --fake-provider --browser-smoke --remote-debugging-port=9223
```

In a second terminal, run `npm run test:desktop:window`. The `--browser-smoke` flag reads public `example.com` through installed Edge or Chrome, so that part needs network access. The test uses only synthetic project and chat data. Close the Electron window before relaunching and check that `test-results\desktop-session-1\instance.lock` is gone. The focused lifecycle, path, navigation and migration checks are `npm run test:desktop`.

For disposable export checks with `--fake-provider`, set `ATLAS_DESKTOP_DOWNLOAD_DIR` to an existing empty folder under `test-results` before launch. The normal desktop app defaults the Save dialog to the user's Downloads folder. `npm run test:desktop:window` checks the renderer, reports, chat, diagnostics version, keyboard dialog behavior, responsive widths and navigation. The browser UI scripts are `node tests/chat-ui.mjs`, `node tests/questions-ui.mjs`, and `node tests/delete-project-ui.mjs`; they require installed Edge or Chrome and use synthetic data only.

For an unattended migration smoke with disposable source data only, set `ATLAS_DESKTOP_LEGACY_DIR` to a copy of a source installation folder (or its `data` folder), point `ATLAS_DESKTOP_PROFILE_DIR` and `ATLAS_DESKTOP_DATA_DIR` to new disposable folders, then run `npm run desktop -- --fake-provider --migration-smoke`. This development-only flag accepts the import choice automatically. A packaged build always asks the user on its first empty workspace. If an import fails, the original source database remains in place; close any source app before retrying.

Optional environment variables: `ATLAS_PORT`, `ATLAS_DATA_DIR`, `ATLAS_BROWSER` (path to installed Chrome/Edge). The standard Windows launcher uses port 4318.

## Fire protection coverage (version 1.3)

Fire protection and matching custom specialties use an explicit NFPA screening profile. Baseline targets include NFPA 1, 3, 4, 10, 13, 14, 20, 22, 24, 25, 70, 72, 80 and 101. Project context adds relevant candidates (for example, data centers add 75, 2001, 855, 110, 111, 30 and 37). These are research targets, not an adopted-code list; the profile contains no editions. Other disciplines keep their existing research workflow.

Both code research and Opus verification must return one finding per screening target. The final report separates NFPA findings, scope applicability and evidence status, with edition and adoption source IDs. Missing/grouped findings cannot satisfy coverage; missing editions remain unconfirmed. Source support for an adopted edition requires matching quotations for the adoption chain and the individual standard/edition. These deterministic checks do not certify the legal meaning of a quotation. Conditional scope still generates a follow-up question. NFPA 13, 13D and 13R are distinct designations.

On an existing fire protection project, open **Codes & standards → Research NFPA standards**. This paid, budget-checked action reopens codes, verification and report generation, keeping completed jurisdiction/contact stages, sources, the previous report, recorded costs and cumulative search/read limits. Real-time and batch are both available. A project with unfinished initial jurisdiction/contact work should use normal continuation first. Old signed conversations retain their original tool schema; the focused refresh starts fresh conversations. Existing reports are never silently rewritten or submitted for paid research.

The PDF includes an NFPA section; Excel adds an **NFPA standards** worksheet; JSON includes `fireStandards` and `fireProtection`. Diagnostics record checklist failures and final NFPA coverage totals. The compact report grammar remains a single repeated row shape.

Research-profile references: [NFPA publication catalog](https://link.nfpa.org/all-publications), [NFPA energy storage guidance](https://www.nfpa.org/en/for-professionals/for-business/creating-a-culture-of-safety/commercial-ess-and-pv-safety), [Virginia incorporation-by-reference rule](https://law.lis.virginia.gov/admincode/title13/agency5/chapter63/section10/). These explain screening and adoption tracing, not project-specific adopted editions.

## Evidence recovery (version 1.4)

Research can save exact source-linked claims and outstanding questions with `save_progress`. Automatic checkpoints also retain source IDs, public progress text, retrieval errors, and saved-review lookups. Context recovery and explicit continuation retain costs and evidence; previous reports are not rewritten automatically. Large saved transcripts remain in their original attempt records. The input ceiling stays 90k and the overall spending, search, reading, and research-round limits still apply.

Evidence selection allocates text only to sources that contain retrieved text, redistributes unused document shares, and prioritizes project-location matches, adoption/application clauses and exact claim quotations. Selected spans retain source offsets. The final reviewer can request a saved source by ID, query or offset instead of treating excerpt omissions as missing research. Public webpage links are filtered and bounded; repeated downloads use a short-lived bounded in-memory cache, and overlapping saved text is merged.

Independent `read_source` calls run in groups of up to two per response. Admission reserves each source read before fetching, including across simultaneously running stages; project and verification limits remain enforced. Results and source registration are saved in call order, while one failed read does not discard successful siblings. Identical in-flight downloads share retrieval work. Progress updates, completion, browser rendering and visual PDF inspection remain ordered. Cancellation saves already-started reads and prevents subsequent groups. The existing two-task ceiling bounds total concurrent source reads to four.

NFPA edition checks accept title-before-year adoption wording while rejecting neighboring-standard, ordinance-date and parent-code-year matches. Failed adoption checks explain the specific missing evidence. The NFPA summary separates scope-dependent findings, unresolved applicability, and evidence needing confirmation; these counts can overlap. Reports also identify unfinished research stages separately from substantive AHJ questions. Diagnostics include context restarts, checkpoint availability, search-limit errors, and input counts before/after rebuilding a request.

`node --test tests/evidence-recovery.test.mjs` covers context and search recovery, spending-preserving continuations, bounded review lookups, targeted document retrieval, excerpt selection and NFPA false positives. All tests are offline. `node tests/replay-saved-run.mjs <project-id>` optionally checks a saved run read-only without sending provider requests or changing its report.
