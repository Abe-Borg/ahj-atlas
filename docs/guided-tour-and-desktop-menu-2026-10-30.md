# A guided tour, and a menu bar that does something — October 30, 2026

**Before.** A new user met the window cold: the User guide described every control in prose, but nothing showed them where each one was or what it did on a real report. The desktop window carried Electron's default menu bar, whose File, Edit, View and Window menus held generic window, clipboard and developer commands and nothing for AHJ Atlas.

**Now.** **Guided tour** in the top bar, **Help → Take the guided tour** in the desktop menu, and the User guide's chapter links walk the window on a practice project, one real control at a time. The menu bar has File, View and Help menus whose every item runs an AHJ Atlas action.

## The tour

Adapted from Spec Surgeon's guided tour (its `frontend/src/lib/tour.ts`, `useTour.ts`, `TourOverlay.tsx` and `capabilities.ts`), under the same three rules: nothing of the user's is touched, nothing is pretended, and nothing is spent.

- **The practice project** (`lib/tour.mjs`). Sampleton, a fictional hyperscale data center (fire protection, about 300,000 square feet, preaction in the data halls, a diesel fire pump, lithium-ion UPS batteries, diesel generators). `Tour.start` builds it in `new Store(':memory:')`, so it is never written to the data folder, never in `/api/projects`, never in spending and never seen by the engine. `buildPracticeProject` uses the production paths: `Store.create`, `Store.source` for four fictional City pages and one search lead, `addDocument` for an owner standard standing in for a document the user adds, `validateReport` (which sets every evidence status and adds the NFPA screening questions), `Store.saveQuestion` (one answered, one dismissed, then the research context that used them, so **Research NFPA standards** shows), and `proposeAction` and `applyAction` (a note card applied, an answer card waiting). The result: a verified jurisdiction, 21 NFPA findings (NFPA 13 at its 2025 edition through a local amendment; NFPA 1 and 101 not applicable; six that depend on project scope), a conflicting pre-submittal threshold, five open questions, one note and two recorded replies. Every text says it is fictional, every link is on `example.com`, and the tests check that the recorded replies quote only what their sources say.
- **Routing** (`server.mjs`). A request for `/api/projects/<practice ID>…` goes to `Tour.route`: the project detail (`projectDetail`, shared with saved projects), the chat view and the four exports are answered from the practice store; an image is a 404. Any other method is refused with 409 and `TOUR_REFUSAL` right after the token check, before an upload or JSON body is read. `/api/tour` (status and the finished version), `/api/tour/start` (idempotent, so a reload or a second tab gets the same project), `/api/tour/end` (only for the tour's own ID) and `/api/tour/finished` (`Store.setTourFinished`, kept in the settings row) are the tour's own routes. `closeApp` ends the tour.
- **The page** (`public/tour.js`). Seven chapters, 33 steps, each with an anchor (`data-tour`), the capabilities it teaches, a title and a few sentences; numbers come from `public/trust-facts.js`. `createTour` runs the lifecycle (start, show a step, chapter break, back, end, resume) and the overlay: a spotlight cut out of a dim layer, clipped to the scroll containers that hold the control (the chat history), and a draggable card placed beside it. A step with no anchor, or whose control is not on screen, stands in the middle of the window and says so. Escape asks before ending; a dialog or the chat panel takes Escape first. The end confirmation is a native `<dialog>`.
- **The window during the tour** (`public/app.js`). The host gives the tour `snapshot`, `show`, `restore`, `changed` and `setFinished`. The sidebar shows the practice project above the user's projects, which are disabled with a reason. The new-project form shows the practice values (`PRACTICE_FORM`, pinned to `PRACTICE_INPUT`), never captured as the user's draft, with **Start research** held, since it would create a real project in the user's workspace. The chat panel shows a recording note and a **Recording** label, and its composer is held. The chat panel's remembered place is not written while the tour runs. A notice above the practice project and the breadcrumb say what it is.
- **The place and the finish.** `ahj-atlas.tour-progress` in browser storage holds the tour version, the practice project's ID, chapter, step and the view set aside, so a reload resumes; a mismatch ends the server's tour. A reload still clears an unsent new-project draft, which is page memory as before. Finishing posts `TOUR_COMPLETION_VERSION`, which stops the button pulsing.
- **The capability contract** (`public/capabilities.js`). Every end-user control carries a literal `data-capability`; `tests/tour.test.mjs` fails when a capability is carried but untaught, taught but not carried, or a step's anchor is missing from the page. A new control needs its capability and its tour step in the same change.

## The menu bar

`desktop/menu.mjs` builds File (New research, Export addresses…, API and spending…, Exit), View (the five report tabs, Chat with Atlas, zoom, full screen, Reload page) and Help (Take the guided tour, User guide, Why trust it?, Diagnostics…, Check for updates… when packaged, About AHJ Atlas). `startDesktop` installs it when given Electron's `Menu`.

- **Page commands.** `menuRunner` sends only names in `MENU_COMMANDS`, as `dispatchEvent(new CustomEvent('atlas-menu',{detail:"<name>"}))` through `executeJavaScript`; no preload script or IPC channel is added, and the renderer keeps its sandbox and context isolation. From another page of the app (the User guide) it opens the workspace first. `public/app.js` waits for its first load, closes any open dialog and runs the button's own code.
- **Window commands.** Zoom, full screen and reload use Electron's roles. Reload stays: it is the way back if the page stops responding, and the page's own error message tells the user to reload.
- **Exit** calls `window.close()`, so the existing confirmation while research or chat is active still asks.
- **No Edit or Window menu.** On Windows, text fields keep their clipboard and undo keys without one. A macOS development run gets the standard application and Edit menus, which it needs for those keys.
- **Labels** spell "and": Windows reads an ampersand in a menu label as a mnemonic.

## Trust surfaces

Two runtime cards (U33, U34) and their ledger rows; the local-work list names the tour; the local-files row names the browser storage the page keeps and the finished tour version.

## Tests

`tests/tour.test.mjs` (practice project statuses and honesty, isolation, every refusal, the finished version, the capability and anchor contract, facts-only numbers, menu commands with page actions), `tests/tour-ui.mjs` (every step in a browser, holds, refusals, exports, Escape, reload, Back, chapter links, narrow layout, the user's view returned, no model calls), and `tests/desktop.test.mjs` (the menu template, command delivery, Exit and installation). The Electron menu itself was checked with test doubles; a run of the packaged Windows app is the remaining check.
