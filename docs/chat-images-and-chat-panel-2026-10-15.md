# Chat images and the floating chat panel — October 15, 2026

**Before.** Chat with Atlas was a tab inside the project page: a heading and two explanatory paragraphs, a 580-pixel conversation box, then a composer with a three-row message box, the attachment block and its help text, a wide Reply depth select, a cost disclosure and the Send button. Reading a finding on another tab and asking about it meant switching back and forth. A message could carry documents (PDF, HTML, text) but not pictures, so a photographed plan review comment, a marked-up detail or a screenshot of a permit portal had no way in.

**Now.** Chat with Atlas is a floating panel beside the report, and a message can carry up to five images alongside up to five documents.

## The panel

- **Opening.** **Chat with Atlas** in the project header and a launcher at the bottom right of the window open the panel; the launcher shows **Replying…** while a reply runs. The panel is rendered into its own element outside the workspace (`#chat-dock`), so it stays open across the Overview, Contacts, Codes & standards, Sources and Activity tabs and across projects. The project page's tab list no longer has a chat tab; `state.tab` never holds `chat`.
- **Moving and sizing.** Drag the header to move it; the corner handle (CSS `resize: both`) resizes it; **Expand** fills the workspace; **Minimize** and **Escape** return it to the launcher. Position, size, open state and expanded state are kept in this browser's `localStorage` (`ahj-atlas.chat-dock`) and clamped to the window on every placement. On a narrow window (≤ 760 px) it fills the screen and cannot be dragged or resized.
- **Rendering.** `renderChat()` runs at the end of `renderProject()`. It compares the generated HTML with what it last rendered and skips the DOM when nothing changed, which is most refreshes. The draft is set on the textarea after rendering rather than rendered into the HTML, so typing never forces a re-render. When it does re-render, focus and selection, the conversation's scroll position (bottom-following when the user was at the bottom) and open disclosures are restored, as the tab did before.
- **Composer.** One rounded input: an auto-growing message box (Enter sends, Shift+Enter starts a new line), a Send button, and a toolbar with **Attach document**, **Attach image** and the Reply depth select. Attachments appear as chips (documents) and thumbnails (images) above the box. The two explanatory paragraphs moved into the **How this chat works and what it costs** disclosure; an empty conversation shows three starter questions that fill the message box. Opening a cited source or **Review Activity** from the panel switches the workspace tab and un-expands the panel so the result is visible.
- **Ask Atlas** opens the panel and starts the reply as before.

## Images

- **One route, prepared locally.** `POST /api/projects/:id/images` takes the raw file like the documents route. `addChatImage` (`lib/images.mjs`) detects the type from the bytes (PNG, JPEG, GIF, WebP; anything else is refused with a pointer to Attach document), decodes it with `@napi-rs/canvas`, scales it to at most `CHAT_LIMITS.imageEdge` (1,568) pixels on the long side and about `CHAT_LIMITS.imagePixels` (1,150,000) pixels in all, which is what the API would scale it to anyway, and re-encodes it as PNG (PNG and GIF), JPEG or WebP. The decoder applies a JPEG's EXIF orientation, so a phone photo is stored upright, and the re-encoded file carries no metadata: a photo's location, camera and date tags never leave this computer. A lossless result above `CHAT_LIMITS.imageStoredBytes` (2 MB) is flattened to JPEG. The input limit is `CHAT_LIMITS.imageBytes` (20 MB).
- **Identity and storage.** The stored bytes' SHA-256 prefix is the image ID, so the same picture attached twice is one row in the new `chat_images` table (project, id, name, media type, size, bytes). `GET /api/projects/:id/images/:imageId` serves it to the page with a long immutable cache header (the ID is content-addressed); `DELETE` removes an image that no sent message carries and answers 409 for one that a message carries. Deleting a project deletes its images. Images are not sources: they are not in the register, exports or the research evidence.
- **The message carries IDs.** `POST /api/projects/:id/chat` accepts an optional `images` array. `attachedImages` accepts at most `CHAT_LIMITS.images` (5) distinct IDs of this project's images, refuses them with an Ask Atlas `questionId`, and saves `{id, name, width, height}` in the new `chat_turns.images` column. A repeated send with the same `clientId` must name the same images in the same order.
- **What the model sees.** `chatPayload` places each image as a base64 `image` block immediately before the message text, in the latest message and in that turn's history in later replies, so follow-up questions can still look at the picture while the turn is within the recent-history budget; each image counts toward that budget as about one token per 750 pixels. One request carries at most `CHAT_LIMITS.imageRequestBytes` (20 MB) of encoded image data: the latest message's images always go, and earlier turns keep theirs, newest first, while they fit, which keeps a photo-heavy conversation under the API's 32 MB request limit. `storedPayload` replaces each image's data with its size in the request saved with the attempt (`attempts.payload`), which recovery and diagnostics read but which never leaves this computer, so a reply of twenty requests does not store twenty copies of its images. `userText` appends `Images I attached to this message (sent as the image blocks just before this text, in this order):` and a JSON list of `{name, width, height}`, so the model can refer to a picture by name. The note comes from saved data, so the cached history stays byte-identical. The system prompt says what an image is and is not: read it closely, transcribe or describe it, treat text read from it as information the user provided with no source ID, and say when it is unreadable. `read_project` with `conversation` lists each turn's images by name and size.
- **UI.** Images are chosen with **Attach image**, pasted into the message box (a `paste` event with image files) or dropped on the composer (image files go to the image route, others to the document route). Unsent images live in page memory beside the draft; removing one deletes it from the project. The sent message shows thumbnails that open full size in a dialog. **Try again** on a declined reply sends the same images. Token counting includes the images, so the reply's estimated cost does.

## Verification

- `node --test tests/chat-images.test.mjs`: bytes-based type detection, scaling, a sideways phone photo stored upright with its EXIF block dropped, refusals, authorization, project isolation, removal before and after sending, message validation, the blocks and note in the payload and in later history, retry with the same images, and deletion with the project.
- `node --test tests/chat.test.mjs`, `tests/trust.test.mjs` (the quoted limits) and the rest of `npm test` pass unchanged.
- `node tests/chat-ui.mjs` (real browser, fake provider): everything it covered before through the panel, plus a refused text file chosen as an image, a pasted screenshot scaled and shown from the app's copy, a chosen image removed before sending, Enter sending a message whose payload carries the image before the text, the thumbnail opening full size and surviving a reload, and the panel staying open across tabs, minimizing to the launcher, expanding, dragging, keeping its place after a reload, and Escape.
